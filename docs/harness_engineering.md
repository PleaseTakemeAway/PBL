# 목표: 로컬 LLM 과 하네스 엔지니어링

이 프로젝트(PBL 수업 과제)가 최종적으로 보이려는 것과, 2026-10-22 기준으로 어디까지 와 있는지를 정리한다.

## 1. 목표

> 값싼 로컬 LLM 여러 개를 써도, 하네스를 잘 만들면 원하는 결과를 낼 수 있다.

여기서 원하는 결과는 도면을 읽어 형상과 치수를 알아내고, 전개도와 커팅플랜·구매의뢰(POR)까지 만드는 것이다. 처음에는 무엇이 필요한지 찾느라 시행착오가 많으므로 Claude 를 썼다. 최종적으로는 orchestration 과 각 작업을 모두 로컬 모델이 맡고, 그 결과가 쓸 만하다는 것을 숫자로 보이는 것이 목표다.

### 1.1 하네스

이 문서에서 하네스는 모델 바깥에서 모델이 일을 제대로 하게 만드는 장치 전부를 말한다.

| 요소 | 뜻 |
|---|---|
| 작업 분해 | 큰 일을 단계로 나누고, 모델에게는 좁고 확인 가능한 판단만 맡긴다 |
| 입출력 계약 | 단계마다 입력과 출력 형식(JSON 스키마)을 정하고, 모델 출력은 스키마로 받는다 |
| 맥락 | 단계마다 필요한 도메인 지식(skill 문서), 그림, 앞 단계 결과만 골라서 준다 |
| 검증과 폴백 | 모델 답을 코드로 검사하고, 틀리면 결정적 방법으로 대신하거나 사람 확인으로 넘긴다 |
| 보완 장치 | 검증 오류를 붙여 다시 묻기, 여러 번 묻고 다수결, 다른 모델로 교차 확인 |
| 기록 | 모든 모델 호출의 입력·원문·판단 근거를 남겨 나중에 다시 보고 재현한다 |
| 평가 | 정답이 있는 세트로 단계별·최종 지표를 잰다. 바꿀 때마다 전후를 비교한다 |
| orchestration | 어떤 단계를 어떤 모델로 언제 다시 부를지 정한다. 고정 순서일 수도, 모델이 정할 수도 있다 |

### 1.2 성공 기준

- 같은 평가 세트, 같은 하네스에서 로컬 모델의 지표가 Claude 와 비슷하다. 차이는 단계별로 보인다.
- 하네스 요소마다 켜고 끈 결과(ablation)가 있어서, 어떤 장치가 몇 점을 올렸는지 말할 수 있다.
- orchestration 도 로컬 모델이 하고, 고정 순서보다 나쁘지 않다.
- 위 실험을 다른 사람이 명령 몇 줄로 다시 돌릴 수 있다.

## 2. 지금 상태

두 코드가 있고 서로 연결돼 있지 않다 ([execution_flow.md](execution_flow.md)).

| 요소 | v3 도면 판독기 (`cutplan_agent/reader/`) | v2 워크오더 에이전트 (`cutplan_agent/agent/`, `skills/`) |
|---|---|---|
| 작업 분해 | 13단계 ([reader/stages.md](reader/stages.md)). 모델은 OCR 1곳(표제란 받아쓰기)과 추론 4곳(표제란 정리, 뷰·형상 판단, 전개 파라미터, 복원 후보 확인)에서만 쓰고, 기하·전개 계산·복원은 코드가 한다 | skill 25개, 4계층 (인식·관계·계산·검증) |
| 입출력 계약 | 모델 응답은 공통 JSON 봉투 ([`vlm_output.py`](../cutplan_agent/reader/vlm_output.py)). 로컬 서버는 xgrammar 로 스키마를 디코딩 단계에서 강제한다 | Anthropic structured output, tool 인자 스키마 |
| 맥락 | 단계마다 붙일 skill 문서가 고정돼 있고 sha256 을 기록한다 ([`knowledge.py`](../cutplan_agent/reader/knowledge.py)) | `cutplan_agent/knowledge/*.md` |
| 검증과 폴백 | 모델이 낸 뷰 번호·종류를 실제 후보와 대조하고, 위치 기반 라벨과 다르면 review 에 남긴다. 전개 길이는 모델이 계산하지 못하게 하고 코드가 계산한다. 복원 후보는 검증기 순위가 우선이다. 모델이 없거나 실패해도 끝까지 돈다 | L4 검증 skill, 사람 확인(`ask_human`) |
| 보완 장치 | 없다. 한 번 묻고, 틀리면 폴백 | Claude 의 tool 루프에 맡긴다 |
| 기록 | 모델 호출마다 원문·검증 결과·시간·skill 문서. 단계 파일(`stages/*.json`) | Trajectory (`state.py` 의 `@logged`) |
| 평가 | 합성 도면 30장의 `label.json`: 형상 분류 정확도, 전개 블랭크 1% 이내 | KD25038 smoke test, `run_eval.py` 가 사람 커팅플랜과 비교. 입력과 정답이 짝지어진 실도면 세트는 회사에서 받은 2건뿐이다 ([data/cutplan_cases.md](data/cutplan_cases.md)) |
| orchestration | 기본은 LLM 없이 순서가 코드에 고정 ([`stages/run.py`](../cutplan_agent/reader/stages/run.py)). 2026-10-23 부터 모델이 단계를 tool 로 부르는 [`orchestrator.py`](../cutplan_agent/reader/orchestrator.py) 도 있다 ([reader/orchestrator.md](reader/orchestrator.md)) | Claude (`tool_runner`, [`orchestrator.py`](../cutplan_agent/agent/orchestrator.py)) |
| 모델 | OCR·추론 두 역할. OpenAI 호환 서버(vLLM)나 Anthropic. 기본값은 둘 다 로컬 | 전부 `claude-opus-5-5` 하나 ([`config.py`](../cutplan_agent/config.py)). Anthropic 전용 기능(beta `tool_runner`, `effort`, server-side fallback)을 쓴다 |
| 결과 | 로컬 모델(DeepSeek-OCR-2 + Qwen3.6-27B)로 합성 30장 중 27장 형상 분류 (동료 2026-10-18 실행) | API 없는 smoke test 통과. VLM 경로(L1·L2)는 기록상 실행된 적 없음 |

### 2.1 판단

v3 판독기는 고정 순서 workflow 의 하네스로는 갖춰진 편이다. 모델 일을 좁은 판단으로 줄였고, 출력 형식을 서버에서 강제하고, 검증과 폴백이 있고, 모든 호출을 기록하고, 정답 세트로 잰다. 로컬 모델 27/30 은 이 구조에서 나왔다.

목표 기준으로는 아직 부족하다.

1. **약한 모델을 보완하는 장치가 없다.** 하네스 엔지니어링의 핵심 주장(값싼 모델 + 좋은 하네스)을 보이려면 재요청, 다수결, 교차 확인 같은 장치와 그 효과 측정이 있어야 한다. 지금은 한 번 묻고 틀리면 폴백이다.
2. **단계별 지표가 없다.** 최종 형상과 전개도만 잰다. 동료 결과 `cone_0019` 에서 표제란 OCR 이 `SYN-00019` 를 `SYN-000` 으로 자른 것 같은 단계 오류는 기록을 열어 봐야 보이고 숫자로 나오지 않는다.
3. **모델을 작업마다 고를 수 없다.** 추론 모델 하나가 네 작업을 모두 맡는다. `max_tokens` 1500, `temperature` 0 은 코드 기본값이고 설정 파일이 없다 ([`vlm.py`](../cutplan_agent/reader/vlm.py) `VLMConfig`).
4. **orchestration 을 하는 로컬 모델이 없다.** v3 는 순서가 고정이고, v2 의 orchestration 은 Claude 전용 기능에 묶여 있다.
5. **평가 세트가 작다.** 합성 30장뿐이고, 실제 KDM 도면에는 v3 용 정답이 없다. Claude 와 로컬 모델을 같은 하네스로 비교한 표도 없다. `runs/reader/data_v3_claude_batch_10141611` 은 이름으로 보아 Claude 배치지만, 어떤 코드와 설정으로 돌렸는지 아직 확인하지 않았다.
6. **끝까지 이어지지 않았다.** v3 는 전개도에서 끝나고, 네스팅·POR 은 v2 에만 있다.
7. **v3 는 실도면을 부품 단위로 나누지 못한다.** reader 는 "도면 1장 = 부품 1개"를 전제로 한다. 실제 상세 도면은 한 장에 부품이 여럿이라, 2026-10-23 에 S-2120 4장을 모델 없이 돌렸을 때 3장이 08·11 에서 멈췄다. 도면의 부품표를 읽어 설비 단위 부품 목록을 만드는 단계가 v3 에 없다 ([v4.md](v4.md)).

| # | 일 | 상태 |
|---|---|---|
| 1 | v3 판독을 단계별 스크립트로 나눈다. 단계마다 파일을 남기고 따로 다시 돌릴 수 있게 한다 | 2026-10-22 `reader-stages` 브랜치. [reader/stages.md](reader/stages.md) |
| 2 | 단계별 평가: 단계 파일을 `label.json` 과 비교한다 (표제란 필드, 뷰 라벨, 형상, 전개 파라미터). 정답에 없는 항목은 라벨부터 보강한다 | |
| 3 | 작업별 모델 설정: 단계마다 모델, 엔드포인트, `max_tokens`, `temperature`, skill 문서를 설정 파일로 정한다 | |
| 4 | Claude 대 로컬 비교표: 같은 하네스로 합성 30장을 돌려 단계별로 비교한다 | |
| 5 | 보완 장치: 검증 오류를 붙여 다시 묻기, N회 샘플 다수결(형상 분류), 두 번째 모델 확인. 하나씩 켜고 끄며 효과를 잰다 | |
| 6 | 로컬 orchestrator: 단계 함수(`stages/*.py` 의 `run`)를 tool 로 노출하고, 로컬 모델이 tool 호출 루프로 단계를 고르고 다시 부른다 (vLLM 의 OpenAI 호환 tool calling). 고정 순서 `run.py` 가 기준선이다 | 2026-10-23 `reader-agent` 브랜치에 첫 판. 로컬 Qwen3.6-27B 가 schema 모드로 cone_0019 를 끝까지 돌렸다. `native` 모드와 30장 비교는 아직. [reader/orchestrator.md](reader/orchestrator.md) |
| 7 | v2 뒷단(전개 → 분할 → 네스팅 → POR)을 v3 단계 뒤에 잇고, 최종 산출물까지 로컬로 돈다 | |

## 4. 하네스를 만들 때 지킬 것

- 계산은 코드가, 판단은 모델이 한다. 모델에게 길이나 각도를 계산시키지 않는다.
- 모델 출력은 스키마로 받고 코드로 검사한다. 실패도 기록한다.
- 단계는 파일로 입출력한다. 한 단계만 다시 돌릴 수 있어야 비교와 디버깅이 된다.
- 정답은 추론이 끝난 뒤에만 읽는다 ([`batch.py`](../cutplan_agent/reader/batch.py) 의 `finally`).
- 바꿀 때마다 같은 세트로 전후를 비교하고, 근거를 커밋 메시지에 남긴다 ([AGENTS.md](../AGENTS.md) 2절).
