# v4: 실도면을 부품표부터 읽기

v4 는 v3 도면 판독기(reader)를 실제 설계 도면에 쓸 수 있게 고치는 작업이다. 2026-10-23 에 시작했다. 버전 이름은 문서에서만 쓰고, 코드의 폴더·파일 이름에는 넣지 않는다 (하는 일로 짓는다). 옛 상태는 git 으로 본다.

이 문서는 v4 를 시작한 근거와 계획이다.
- 근거: 회사에서 받은 설비 S-2120 의 설계 도면 4장(`test_data/cases/S-2120/input_drawings/`)을 v3 reader 에 모델 없이(`--no-vlm`) 넣어 봤다 (2~4절). 정답인 `CP.dwg` 는 입력에 넣지 않았다. D-1203 은 6절에 적은 이유로 돌리지 않았다.
- 기존 `test_data/KD23009` 의 몸통 도면 1장도 같은 방법으로 돌렸다 (3절).
- v3 의 점수를 낸 합성 도면 30장이 무엇을 재는지 따로 따져 봤다 (4.5절).
- 같은 도면의 부품표(PART LIST)를 코드로 읽을 수 있는지, 읽은 값이 정답 커팅플랜과 맞는지 대조했다 (5절).
- 계획: 8절.

## 1. 요약

- reader 는 "DXF 1장 = 부품 1개, 3면도"를 전제로 만들어졌다 (합성 도면 `data_v3/synthetic`). 실제 상세 도면은 한 장에 여러 부품이 있어서 이 전제가 맞지 않는다. S-2120 상세 도면 3장은 커팅플랜에 나온 판재 품번만 장마다 4~13종이다.
- 4장 중 1장(GA)만 13단계를 끝까지 돌았고, 그 1장도 시트 전체를 부품 하나로 봤다. 나머지 3장은 08 또는 11 에서 멈췄다. KD23009 몸통 도면은 오류 없이 끝났지만 뷰 하나가 도면 틀의 약 78% 를 덮었다. 오류가 없다고 맞게 읽은 것은 아니다.
- 모델이 없으면 형상 분류(06)를 대신하는 코드가 없다. 그래서 합성 도면에서도 전개(09·10)를 건너뛴다. 모델 없이 되는 것은 DXF 읽기, 표제란 일부(축척·재질), 뷰 후보 묶기, 위치로 뷰 이름 붙이기다.
- 이 한계는 모델 성능이 아니라 단계 설계에서 온다. 06 은 시트 하나에 형상 하나를 묻고, 11 은 방향마다 뷰 하나를 받는다 (4절).
- 상세 도면 3장의 부품표는 DXF 안에 열 위치가 일정한 TEXT 로 있어서 코드로 읽을 수 있다. 커팅플랜의 부품 라벨은 `<설비>-<도면 번호> <품번>` 이라 부품마다 부품표 한 행을 가리킨다. 그 행에서 읽은 재질·두께·수량이 커팅플랜 값과 22건 중 21건 같다 (5절). 부품 목록과 재질·두께·수량은 부품표만으로 만들 수 있다는 뜻이다.
- 부품표의 SIZE 칸에는 판재의 두께만 있고 가로·세로가 없다. 크기는 뷰의 치수에서 읽어야 한다.
- v2 의 판재 판정 규칙(`normalize_bom`)을 이 부품표에 적용하면 형강(L200x200x14, L75x75x9)과 와셔도 판재로 본다 (5.4절).
- v3 의 "형상 분류 27/30" 은 합성 도면 30장의 점수다. 합성 도면은 실도면보다 훨씬 쉽고, 전개 정답은 생성기의 식이라 실제 절단 치수와의 일치를 뜻하지 않는다. 합성 30장은 회귀 테스트로 두고, v4 의 점수는 실도면(`test_data/cases/`)으로 잰다 (4.5절).

## 2. 실행 방법

레포 루트에서 실행한다. reader 의 배치(`main.py --batch`)와 단계 실행기는 `.dxf` 만 받으므로 ([`batch.py`](../cutplan_agent/reader/batch.py)) DWG 를 먼저 DXF 로 바꾼다. `dwg2dxf` 는 LibreDWG 0.14 다 ([getting_started.md](getting_started.md)).

```bash
OUT=runs/reader/real_drawings/S-2120
mkdir -p $OUT/dxf
for f in test_data/cases/S-2120/input_drawings/*.dwg; do
  n=$(basename "$f" .dwg); n=${n%%_R0*}
  ~/.local/bin/dwg2dxf -y -o "$OUT/dxf/$n.dxf" "$f"
done
for d in $OUT/dxf/*.dxf; do
  n=$(basename $d .dxf)
  PYTHONPATH=. uv run python cutplan_agent/reader/stages/run.py $d $OUT/${n#VP-S-2120-} --no-vlm
done
```

- 도면마다 `$OUT/DWG-00N/stages/*.json` 이 생기고, 뷰를 어떻게 나눴는지는 `analysis/sheet.png` 에서 본다. 단계 파일 읽는 법은 [stages.md](reader/stages.md) 4절.
- 실패한 도면은 종료 코드 1 로 끝난다. 두 번 돌려 단계별 상태가 같은 것을 확인했다.
- 비교용 합성 도면: `PYTHONPATH=. uv run python cutplan_agent/reader/stages/run.py data_v3/synthetic/cone_0019/cone_0019.dxf <작업 폴더> --no-vlm`
- KD23009: `test_data/KD23009/input_drawings/CAD/` 의 DWG 3장을 같은 방법으로 바꿔 `runs/reader/real_drawings/KD23009/dxf/` 에 두고, 몸통 도면(`VP-E-31230-002_DETAIL OF BODY & SUPPORT LUG_R0`)을 돌렸다. 파일 이름에 공백과 `&` 가 있어 경로를 따옴표로 감싼다.
- 단계를 하나씩 돌리고 표·그림으로 보는 법, 모델 서버를 붙여 돌리는 법은 [reader/quickstart.md](reader/quickstart.md) 에 있다. 실도면도 같은 명령에 위 DXF 를 넣으면 된다.

## 4. 왜 안 되나: 시트 1장 = 부품 1개

### 4.1 reader 가 전제하는 도면

합성 도면 한 장에는 부품 하나와 그 부품의 정면도·평면도·우측면도, 표제란 하나가 있다. 정답 `label.json` 도 `"class"` 하나와 `flat_pattern` 하나뿐이다. 13단계는 모두 "이 시트의 부품 하나"에 대한 답을 만들고, 출력도 시트 한 장당 형상 분류 하나, 전개도 하나, 3D 모델 하나다.

### 4.2 코드에서 그 전제가 드러나는 곳

| 단계 | 코드 | 전제 |
|---|---|---|
| 06 | [`dxf_adapter.py`](../cutplan_agent/reader/dxf_adapter.py) `label_with_vlm` 의 프롬프트 | `part_class: one of flat, cylinder, cone, …` 로 시트 전체에 형상 하나, `Exactly one region may be front`, `reconstructable_from_views` 도 시트 전체에 하나 |
| 08 | [`reconstruct/models.py`](../cutplan_agent/reconstruct/models.py) `DrawingDocument` 검사 | 뷰가 하나 이상 있어야 한다. DWG-002 는 0개라 여기서 멈췄다 |
| 08 → 11 | `build_document` 의 미러, [`reconstruct/step1.py`](../cutplan_agent/reconstruct/step1.py) `identify_views` | 08 은 left 를 right 로, bottom 을 top 으로, back 을 front 로 뒤집는다. 11 은 방향마다 뷰가 하나여야 한다 |

DWG-003 에는 right 와 left, top 과 bottom 이 함께 있어서, 뒤집고 나면 right 2개, top 2개가 된다. 실제로는 그 뷰들이 서로 다른 부품(맨홀 목, 패드, 플랜지, 데이빗 등)을 그린 것이라 한 부품의 3면도로 묶일 수 없다.

### 4.3 모델을 붙이면 달라질 것과 달라지지 않을 것

- **달라질 수 있는 것:** 모델이 DWG-003 의 일부 뷰를 `section` 이나 `detail` 로 판단하면 방향 중복이 사라져 11 의 오류가 없어질 수 있다. `reconstructable=false` 로 답하면 11 을 건너뛴다.
- **달라지지 않는 것:** 답할 수 있는 칸이 "이 시트의 형상 하나"뿐이다. 예를 들어 DWG-002 에는 커팅플랜에 나온 판재 부품만 13종(SHELL 원통, TOP·BTM HEAD 경판, BASE PLATE·GUSSET 평판 …) 있는데 그중 하나만 고르게 된다. 오류는 없어져도 답의 의미가 맞지 않는다.
- **모델을 붙인 결과 (2026-10-23, S-2120 DWG-003 한 장):** DeepSeek-OCR-2 + Qwen3.6-27B 로 00–13 을 돌렸다. 06 은 형상을 `other` (확률 0.9998), `reconstructable=true` 로 답했고, 뷰 13개 중 9개를 `detail`, 1개를 `section`, 1개를 `table` 로 붙였다. 방향 중복이 사라져 11 의 오류는 없어졌지만 복원 후보는 0개(`no_valid_candidate`)이고, 형상이 `other` 라 09·10 전개는 건너뛴다. 모델은 맞지 않는 입력을 알아채지만 부품 목록을 만들지는 못한다. 다른 도면은 아직 돌리지 않았다.

### 4.4 필요한 것: 시트 → 부품

13단계 앞에 "이 시트에 어떤 부품들이 있고 각각이 어디에 그려져 있나"를 정하는 단계가 필요하다. 실도면에서 이 정보는 두 곳에 있다.

1. **부품표:** 무엇이, 어떤 재질·두께로, 몇 개인지 (5절)
2. **품번 풍선:** 뷰 옆의 `4-1`, `7-2` 같은 표시. 어느 뷰가 어느 부품인지 알려 준다. 부품별 크기를 읽을 때 필요하다

reader 를 버리는 것은 아니다. 01 (엔티티와 위치 읽기)은 부품표 단계의 입력으로 그대로 쓰고, 10 (전개 계산)은 형상과 치수만 있으면 된다. 06·09 는 부품 하나의 영역을 떼어 넣으면 원래 목적대로 쓸 수 있다. 다만 그 영역을 떼어내는 단계가 아직 없다.

### 4.5 v3 의 점수(합성 30장)가 말해 주는 것

v3 의 기준 결과는 합성 도면 `data_v3/synthetic` 30장에서 형상 분류 27장이다 (동료의 2026-10-18 실행). 이 점수를 실도면 성능으로 읽으면 안 된다.

- **생성기가 레포에 없다.** DXF 첫 줄의 주석은 `cutplan_agent_v2 data_v3 generator`, `label.json` 의 출처는 `synthetic:make_data_v3` 인데, 이 생성기는 레포에 없다 ([data/overview.md](data/overview.md) 3절). 라벨을 어떤 규칙으로 만들었는지 코드로 확인할 수 없다.
- **너무 쉽다.** 형상 5종(flat, bent_sheet, cylinder, cone, press_formed)이 6장씩이고, 한 장에 부품 하나를 3면도로 그렸다. 치수도 `cone_0019` 처럼 150, 100 같은 딱 떨어지는 값이다. 실도면의 여러 부품, 부품표, 한글 주석, 비표준 표기, DWG 변환 실패는 하나도 없다.
- **전개 정답이 생성기의 식이다.** 전개도 정답은 실측이 아니라 생성기가 계산한 값이다. 그래서 "1% 이내 일치" 는 생성기와 같은 식을 쓴다는 뜻이다. 실제로 reader 의 경판 원판 계수([`reader/unfold.py`](../cutplan_agent/reader/unfold.py) 의 `HEAD_BLANK_K` = 1.25~1.30)는 회사 계산 문서의 식으로 바꾸지 않고, 이 합성 정답에 맞추려고 그대로 두었다.

합성 30장이 쓸모없는 것은 아니다. 정답이 단계마다 다 있고, 모델 없이 돌리면 결과가 매번 같고, 고객 도면이 없어 공개 레포에서 다루기 안전하다. 그래서 "단계가 고장 나지 않았는가" 를 보는 회귀 테스트로 쓴다. "판독을 잘하는가" 는 실도면(`test_data/cases/`)으로 잰다.

## 5. 부품표 (PART LIST)

### 5.1 위치와 형식

- 상세 도면 3장(DWG-002·003·004)에 부품표가 있다. GA(DWG-001)에는 부품표 대신 NOZZLE LIST 와 MATERIAL SPECIFICATION 이 있다.
- 헤더는 `PART | PART NAME | MATERIAL | Q'TY | (단위) | SIZE / DIMENSION` 이다. DWG-003·004 에는 예비 수량 열 `SP1`, `SP2` 가 더 있다.
- 행은 헤더 위쪽에 쌓이고, 품번 1 이 헤더에 가장 가깝다.
- 그룹 번호는 그룹의 첫 줄에만 있고, 다음 줄은 `-2`, `-3` 만 있다. 앞 번호를 이어 붙이면 정답 라벨의 품번(`S-2120-002 7-2` 의 `7-2`)과 같아진다. 하위 번호가 없는 품번도 있다 (`3 EARTH LUG`).

```
7  -1  SUPPORT BRACING   A36           4  EA  L75x75x9
   -2  GUSSET PLATE      A283-C        8  EA  t10
```

- SIZE 칸: 판재는 두께만 있다 (`t10`). 그 밖에는 형강(`L200x200x14`), 배관(`10" SCH.40S`), 플랜지 규격(`24" ASME B16.5 150# W.N.R.F`), 볼트(`M24x150L`), 지름(`%%C19`)이 있다.

### 5.2 정답 커팅플랜과 대조

커팅플랜의 부품 라벨 `S-2120-002 7-2` 는 도면 `VP-S-2120-DWG-002` 부품표의 품번 `7-2` 를 가리킨다. 그래서 정답 품번이 부품표에 있는 것 자체는 라벨 규칙상 당연하다. 여기서 확인한 것은 두 가지다.
- 받은 입력 도면에 정답 부품이 가리키는 부품표가 빠짐없이 있는가 (`coverage.csv` 와 같은 결과)
- 부품표에서 코드로 읽을 수 있는 재질·두께·수량이 정답과 같은가

정답 `test_data/cases/S-2120/output_cutting_plan/parts.csv` 의 행을 (도면, 품번)으로 부품표 행과 맞췄다. 부품표는 임시 스크립트로 TEXT 를 좌표순으로 뽑아 손으로 읽었다 (레포에 넣지 않았다).

### 5.5 코드로 읽을 때 주의할 것

- **행 간격이 축척에 따라 다르다.** DWG-002 (1/14)는 모델 공간에서 행 간격이 약 98, DWG-004 (1/4)는 약 28 이다. 행을 묶는 허용 오차를 고정값으로 두면 DWG-004 의 행이 모두 한 줄로 합쳐진다. 글자 높이나 헤더 높이에 비례하게 잡아야 한다.
- **한 칸이 두 줄인 경우가 있다.** `STUD BOLT/2HEAVY HEX. NUTS` 아래 줄의 `(W/ YELLOW CHROMATED)` 는 별도 TEXT 다.
- **수량 칸이 둘로 나뉜 행이 있다.** GASKET 은 `2 | 4` 처럼 수량과 예비 수량이 함께 나온다 (SP 열).
- **AutoCAD 제어 코드가 남아 있다.** `%%C` (Ø), `%%D` (°)
- 표 바로 위에 NOTES 와 VENT HOLE 그림의 글자가 있어서, 표의 위쪽 끝을 정해야 한다. 표의 선(LINE)으로 경계를 잡는 것이 안전하다.

### 5.6 knowledge 에 반영한 것

품번과 커팅플랜 라벨의 관계는 사람용 문서([data/cutplan_cases.md](data/cutplan_cases.md) 2절)에만 있고, 모델이 읽는 knowledge 에는 없었다. 2026-10-23 에 다음을 더했다. `skills/01_core_knowledge/` 와 `cutplan_agent/knowledge/` 의 두 사본은 같은 바이트다.

- `drawing_conventions_kr.md` 의 BOM 표 읽기: 헤더 `PART`, 예비 수량 열 `SP1`·`SP2`, 단위 `LOT`, 그룹 번호를 첫 줄에만 적는 표기, 커팅플랜 부품 라벨과 품번의 대응, 판재가 아닌 행(형강·파이프·플랜지·볼트·표준 와셔), 판재로 적혀 있어도 커팅플랜에 없는 부품(확인 중, Q18)
- `nesting_rules.md`: 판 위 부품 라벨 형식

reader 09 단계(`unfold_params`)가 `drawing_conventions_kr.md` 를 프롬프트에 붙이므로, 이후 모델 실행의 입력이 바뀐다. 모델 없는 실행 결과는 바뀌지 않는다.

## 7. 다른 작업과의 관계

- **v2 워크오더 에이전트:** 설비 단위로 도면 읽기 → 부품표 → 전개·분할 → 네스팅으로 가는 흐름이 v2 의 [`system.md`](../cutplan_agent/agent/system.md) ①~④ 에 이미 있다. 부품표는 Claude 가 그림을 보고 표 전체를 옮겨 적고(`vlm_read_page(what="bom")`), `normalize_bom` 이 정리한다. 하지만 이 경로는 기록상 한 번도 실행되지 않았다 ([AGENTS.md](../AGENTS.md) 7절).
- **[execution_flow.md](execution_flow.md) 의 구도:** "v3 는 앞단(도면 판독), v2 는 뒷단(전개·네스팅)" 으로 설명한다. 이번에 보니 앞단 안에서도 단위가 다르다. reader 의 앞단은 부품 단위이고, v2 의 앞단(①②)은 설비 단위다. 실도면에는 설비 단위 앞단이 필요하다.
- **[harness_engineering.md](harness_engineering.md) 로드맵 7번:** "v2 뒷단을 v3 단계 뒤에 잇는다"는 이 사이에 설비 단위 앞단(부품표 → 부품 목록)이 있어야 성립한다.
- **`reader-agent` 브랜치 (reader orchestrator, 2026-10-23):** 단계 함수를 tool 로 감싸 모델이 고르게 하는 orchestration 층이다. 부품표 단계와는 서로 기다릴 필요가 없는 별개의 작업이다. 만나는 곳은 새 단계를 `reader/tools.py` 에 tool 로 등록하는 부분뿐이다.

## 8. v4 계획: 부품표 단계

첫 작업은 v2 의 ② (부품표 → 부품 목록)를 v3 의 단계 방식(단계마다 파일, 코드로 먼저 읽고 모델은 폴백)으로 옮기는 것이다. 코드 이름에는 버전을 넣지 않는다.

1. **부품표 읽기 (도면 1장, 코드만):** reader 01 단계의 `01_read.json` (글자마다 위치와 handle)을 입력으로 받는다. 헤더를 키워드로 찾아 열 경계를 정하고, 행을 묶고, 그룹 번호를 이어 붙인다. 출력은 v2 VLM 출력과 같은 스키마(`BomRowRaw`)에 칸마다 원본 글자의 handle·좌표를 더한 것이다. 표 안에서 어느 칸에도 못 넣은 글자는 따로 남긴다. 도면 번호는 표제란에서 읽고, 못 읽으면 파일 이름을 쓰되 출처를 적는다. 같은 스키마이므로 글자가 없는 PDF(D-1203)는 나중에 OCR·VLM 이 같은 파일을 쓰면 된다.
2. **부품 목록 (설비 단위, 코드만):** 도면별 부품표를 합쳐 `S-2120-002 7-2` 형태로 만든다. 판재 여부·두께·전개 분류는 `normalize_bom` 에서 떼어낸 순수 함수를 쓴다 (`normalize_bom` 은 그 함수를 부르게 바꾸고 smoke test 전후를 비교한다). 행마다 판정 근거를 남긴다.
3. **평가 (`cutplan_agent/eval/`):** 정답 `parts.csv` 와 (도면, 품번)으로 맞춰 찾은 비율, 판재 판정의 정밀도, 재질·두께 일치, 단위 EA 의 수량을 잰다.

S-2120 에서 손으로 본 기댓값은 5.2~5.4절이다: 정답 품번 22/22, 재질·두께 21/22, 지금 규칙 그대로면 형강·와셔가 판재로 더 나온다.

이번 범위 밖: 판재 크기 (뷰 치수와 품번 풍선 읽기), D-1203 (OCR 필요).

v4 의 점수는 실도면 정답(`test_data/cases/`)으로 잰다. 합성 30장은 reader 단계가 바뀌지 않았는지 보는 회귀 테스트로 남긴다 (4.5절).
