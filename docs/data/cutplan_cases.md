# 회사에서 받은 커팅플랜 테스트셋 (`test_data/cases/`)

2026-10-22 에 회사 담당자에게서 설비 2개의 설계 도면과 커팅플랜을 받았다. 담당자 말로는 커팅플랜이 있는 것은 이 두 건이 전부다. 입력 도면과 정답 커팅플랜이 설비 단위로 짝지어 있어서, 기존 `test_data/` 와 달리 입력에서 정답까지 이어서 평가할 수 있다. 데이터는 git 에서 빠져 있다.

## 1. 받은 것과 만든 것

```
test_data/cutting_plan/<설비>/     받은 원본. 다시 만들 수 없으니 지우지 않는다
  *.dwg, *.pdf                     설계 도면 (GA, DETAIL OF BODY, MANHOLE, NOZZLE ...)
  CP.dwg                           커팅플랜
  note.md                          워크오더 번호 한 줄
test_data/cases/                   scripts/build_cutplan_cases.py 가 위 폴더로 만든다
  index.csv, README.md             설비별 요약
  <설비>/
    input_drawings/                설계 도면 (받은 그대로)
    output_cutting_plan/           CP.dwg, CP.dxf, CP.png, qc.png, sheets.csv, parts.csv, pieces.csv
    output_unfold/P<n>.dxf         조각마다 외곽 (pieces.csv 의 piece_id)
    source.csv                     받은 파일의 크기·sha256, 기존 데이터와의 비교, 입력 DWG 를 읽을 수 있는지
    coverage.csv                   정답 부품이 가리키는 설계 도면이 입력에 있는지
```

다시 만들기: 레포 루트에서 `PYTHONPATH=. uv run python scripts/build_cutplan_cases.py`. dwg2dxf(LibreDWG 0.14)가 있어야 한다 ([getting_started.md](../getting_started.md)). 실행할 때마다 `test_data/cases/` 를 지우고 새로 쓴다.

## 2. 두 설비

| | S-2120 | D-1203 |
|---|---|---|
| 워크오더 | KD25021 | KD23079 (설비 38개 중 하나) |
| 입력 | DWG 4 + PDF 4 (GA, BODY & INSULATION SUPPORT, MANHOLE, NOZZLE) | DWG 6 + PDF 6 (GA, BODY & SUPPORT LUG, MANHOLE, NOZZLE 1·2, HEATING COIL) |
| 커팅플랜 형식 | 판재 배치도 (`nesting`) | 부품 전개도 모음 (`unfold_list`). 판재가 없다 |
| 정답 | 판재 8장, 부품 라벨 51개, 조각 69개 | 부품 29개 (속성 글자 26, 형상만 3), 조각 61개 |
| 비교할 수 있는 것 | 판재 규격·수량·중량, 판마다 부품, 부품 외곽 크기 | 부품 목록, 재질·두께·크기·수량, 전개 형상 (쉘, 헤드 2분할, 콘 4분할 …) |
| 비교할 수 없는 것 | | 판재 수, 중량, 배치 |
| 입력에 없는 도면 | 없다 | 없다 |

- S-2120 의 판재 라벨은 `A240-S31803 t8 x 1850 x 4800 1 sh't` 형식이다. 부품 라벨은 `S-2120-002 1-1` (도면 번호와 그 도면의 아이템) 과 그 아래 부품명 두 줄이다.
- D-1203 의 줄 번호 `002-1-1` 은 도면 OTH-002 의 아이템 1-1 이다. 속성 글자 `D=D-1203-2\PN=SHELL\PM=SA240-304L\PT=25\PS=2662x11702.5\PQ=1` 의 `D=` 는 여러 부품에 `D-1203-2` 로 똑같이 들어 있어서 도면 번호는 줄 번호로 정한다. `\P` 는 MTEXT 의 줄바꿈이라 글자는 `D` 도면, `N` 이름, `M` 재질, `T` 두께, `S` 크기, `Q` 수량 여섯 줄이다.
- D-1203 의 헤드 줄에는 `HEAD-TYPE(2:1)`, `I.D3700`, `TL:38` 이 적혀 있고 원판은 `Ø4590` 이다. 헤드 원판 식을 확인하는 데 쓸 수 있다.

## 3. 정답을 읽는 방법

`cutplan_agent/eval/cp_parse.py` 가 CP.dxf 를 읽는다. 규칙과 한계는 그 파일 머리말에 있고, 요약은 다음과 같다.

- 판재: 판재 라벨을 정규식으로 읽고, 크기가 같은 사각형 중 라벨에 가장 가까운 것을 테두리로 잡는다.
- 조각: 닫힌 외곽선 하나다. 블록(INSERT)은 풀어서 쓴다. 조각 안의 닫힌 외곽은 구멍이다.
- 부품 라벨 → 조각 (`parts.csv` 의 `outline`): `label` 라벨을 감싸는 조각, `face` 선을 공유한 부품끼리의 면, `near` 라벨 옆의 조각(추정), `none` 못 찾음.
- 라벨 없는 조각 → 부품 (`pieces.csv` 의 `link`): `copy` 같은 판의 같은 모양, `row` 전개도 모음에서 같은 줄의 유일한 부품. 둘 다 추정이다.
- 결과는 `output_cutting_plan/qc.png` 로 확인한다. 초록 = label, 파랑 = face, 주황 = near, 연두 = copy·row, 빨간 테두리 = 부품에 묶이지 않은 조각.

기존 정답(`Data/_dataset/`)을 만든 툴킷 `cp_extract.py` (`~/dwg2png`, sha256 `1db0888d…`) 를 같은 CP.dxf 에 돌려 비교했다 (2026-10-23).

- S-2120: 판재 8장은 같다. 6장은 판마다 조각 수와 크기(1 mm 반올림)가 모두 같다. `A240-304 t8 x 1150 x 1200` 의 링 조각 20개는 툴킷이 호(ARC)의 bbox 를 시작점·끝점·중심으로만 잡아 높이가 63 으로 작게 나온다 (cp_parse 는 호를 펴서 90). `A283-C t6 x 700 x 1150` 은 툴킷이 `chain_path` 로 표시하고 맞닿은 부품을 두 덩어리(262 x 395)로 뭉쳐 7개를 낸다. cp_parse 는 블록을 풀고 면을 써서 9개를 낸다.
- D-1203: 툴킷은 판재 라벨이 없어 판재·부품을 0 으로 내고, 속성 글자 21건만 `part_tags.csv` 에 남긴다. CONE 4건과 STIFF. RING 은 빠지고, 크기·이름에 MTEXT 서식 코드(`280\fArial|b0|…;x340`)가 남는다. cp_parse 는 26건을 읽고 서식 코드를 지운다 (`280x340`).

## 4. 알려진 문제 (2026-10-23)

담당자에게 물어볼 것은 [company_questions.md](../domain/company_questions.md) 2절에 모았다.

- S-2120 판 8 (`A240-304 t8 x 1150 x 1200`) 의 링 조각 6개 (380.5 x 85.7) 는 부품에 묶이지 않았다. 5-2 INSUL SUP'T RING 열에 있지만 라벨이 붙은 5-2 조각 (283 x 76.4) 과 크기가 달라 추정하지 않았다.
- D-1203 의 입력 DWG 6개는 LibreDWG 0.14 가 DXF 를 TABLES 구간까지만 쓰고 멈춰 ezdxf 가 열지 못한다 (`source.csv` 의 `readable`). 이 환경에서는 같은 이름의 PDF 를 입력으로 쓴다. S-2120 의 DWG 4개는 읽힌다.
- D-1203 의 일부 부품은 속성 글자의 크기와 그려진 외곽이 다르다. M1/24 는 `S=212x1852` 인데 외곽이 250 x 1869.3, N11/24 는 `S=200x1852.3` 인데 230 x 1852.3, 002-3-3 LIFT PAD 는 `S=280x340` 인데 조각 2개가 각각 125 x 340 이다. `parts.csv` 에 `size` (글자) 와 `w`·`h` (외곽) 를 둘 다 둔다.
- D-1203 의 줄 004-2-3, 005-1-3, 005-2-3 에는 속성 글자가 없어 형상만 있다. 005-3-3 RIB 는 `Q=6` 인데 조각은 4개 그려져 있다.
- 받은 D-1203 폴더에는 처음에 `CP.bak` (256,992 바이트, sha256 `dc2998e5…`) 이 있었고, CP.dwg 와 엔티티 종류별 수와 글자가 같았다. 2026-10-23 에 폴더에서 빠졌다.

## 6. 전개 식 확인 (2026-10-23)

받은 도면에서 읽은 치수로 v2 L3 식과 받은 CP 의 값을 비교했다. v2 L3 식은 2026-10-23 부터 회사 담당자의 계산 문서(`skills/01_core_knowledge/shell_cone_head_unfold.md`)를 따른다. 같은 값을 `tests/test_l3_formulas.py` 가 확인한다.

| 부품 | 도면에서 읽은 치수 | CP 값 | 계산 문서 식 | 그 전 v2 식 |
|---|---|---|---|---|
| D-1203 SHELL | ID 3700, t25, 길이 2662 | 11702.5 x 2662 | π(ID + t) = 11702.4 | 같다 |
| S-2120 SHELL | ID 1500, t8 (OD 1516), 길이 1823 | 4738 x 1823 | 4737.5 | 같다 |
| D-1203 HEAD 2:1 | ID 3700, t23, SF 38 | Ø4590 | 4570 (−20) | 4600 (+10) |
| S-2120 TOP HEAD 2:1 | ID 1500, t10, SF 27 | Ø1890 | 1900 (+10) | 1830 (−60) |
| S-2120 BTM HEAD 2:1 | ID 1500, t8, SF 27 | Ø1878 | 1890 (+12) | 1830 (−48) |
| D-1203 CONE 1-3 (2분할) | ID 3700 → 1621.5, 높이 1800, 반각 30°, t22 | 5232.6 x 2553.4 | 5263.7 x 2559.8 | 같다 |
| D-1203 CONE 1-4 (2분할) | ID 1621.5 → 476.4, 높이 991.7, t22 | 2293.2 x 1284.7 | 2324.3 x 1291.1 | 같다 |

- 헤드 식은 2:1 반타원형 1.2 × Dm + 2 × SF + 트림 30 을 10 mm 로 반올림한 값이다. 계산 문서 식으로 거꾸로 구한 트림은 D-1203 46, S-2120 TOP 24, BTM 14 mm 다. 문서의 범위(20~50)와 예시(30)를 보고 30 으로 두었다 (`config.HEAD_TRIM`).
- SF 는 D-1203 OTH-002 의 T.L 위 치수 38, S-2120 DWG-002 의 `T.L TO T.L 1877` 에서 쉘 길이 1823 을 빼고 반으로 나눈 27 이다. D-1203 CP 의 헤드 줄에도 `TL:38` 이 적혀 있다.
- 콘은 CP 값이 **안지름 기준** 전개와 0.1 mm 까지 맞는다 (R1 = ID). 계산 문서와 v2 코드는 평균지름 기준이라 폭이 31 mm 크다. 같은 CP 의 쉘은 평균지름 기준이다. KD25038 의 KDM 배치툴은 쉘도 안지름 기준이었다 ([agent/skills.md](../agent/skills.md) 2절). 어느 부품을 어느 지름으로 전개하는지는 회사 담당자에게 확인해야 한다 ([company_questions.md](../domain/company_questions.md) Q2). 확인 전까지 코드는 계산 문서대로 평균지름 기준이다.
- KD25038 smoke test 의 헤드 원판은 3250 에서 3260 으로 바뀌었다 (실제 3240). 입력의 SF 50 은 도면에서 읽은 값이 아니라 기본값이다.
